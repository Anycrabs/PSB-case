# Юридический ассистент ПСБ — Hack&Change 2026

ИИ-ассистент для юристов: отвечает на вопросы только по базе нормативных документов, ссылается на конкретные пункты и обоснованно отказывается, если данных не хватает.

Стек: Python, FastAPI-микросервисы, Docker Compose, гибридный поиск на эмбеддингах BAAI/bge-m3, Qdrant, DeepSeek V4.1 Flash через OpenAI-совместимый API.

Что сделать руками (ключ, запуск, сабмит) — в [docs/SETUP_LLM_EMBEDDINGS.md](docs/SETUP_LLM_EMBEDDINGS.md).

## Запуск

Нужен Docker (Docker Desktop). Все сервисы поднимаются одной командой, сначала бэкенд, затем интерфейс: `web` стартует только после того, как `gateway` прошёл проверку готовности.

**Без ключа LLM** — чтобы посмотреть интерфейс и проверить, что стенд поднимается (ответы даёт заглушка, по смыслу они неточные):

```bash
cp .env.example .env                       # по умолчанию заглушка LLM и fake-эмбеддинги
docker compose --profile dev up --build    # интерфейс http://localhost:3000
```

**С моделью DeepSeek** — в `.env` указать `LLM_BASE_URL=https://api.deepseek.com`, `LLM_API_KEY=<ключ>`, `LLM_MODEL` (подсказки — в комментариях `.env.example`) и `EMBEDDER_MODE=local`, затем:

```bash
docker compose up --build                  # первый запуск скачивает bge-m3 (~2,3 ГБ)
```

| Адрес | Что там |
| --- | --- |
| http://localhost:3000 | Веб-интерфейс |
| http://localhost:8000/docs | API шлюза (OpenAPI) |

Остановить: `docker compose --profile dev down`.

### Разработка интерфейса без Docker

```bash
cd web && npm ci && npm run dev            # http://localhost:5173, /api проксируется на :8000
```

Бэкенд при этом должен работать на `localhost:8000` (в Docker или локально через uvicorn).

## Сабмит на платформу

```bash
python submission/build_zip.py  # -> dist/submission.zip
```

Архив собран по Техническому регламенту:
- В корне лежат `solution.py`, модули `lc_*.py` (это `legal_core` с переписанными импортами) и `requirements.txt` (`httpx==0.28.1`, `numpy==2.2.6`). Вложенных папок нет.
- `solution.py` читает `{DATA_DIR}/questions.csv` и `knowledge-base.zip`, строит индекс при запуске через `POST {LLM_BASE_URL}/embeddings` и отвечает тем же конвейером, что прототип. Результат пишет в `submission.csv` (`id,answer`, CSV-экранирование, ответ в одну строку, не длиннее 10 000 символов).
- Используются переменные платформы: `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `EMB_MODEL`, `RERANKER_MODEL`, `TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS`, `DATA_DIR`, а также их запасные имена.
- Лимит 20 минут: если прогноз не укладывается в 18 минут, конвейер переключается в быстрый режим. Перед тайм-аутом файл записывается с уже готовыми ответами, пустых ответов нет.
- Если `/embeddings` недоступен, поиск работает на BM25. Если недоступен `/rerank`, остаётся порядок RRF.

Локальная проверка на демо-вопросах организаторов (нужен ключ LLM в окружении):

```bash
DATA_DIR=data/demo EMBEDDER_MODE=fake python submission/solution.py    # создаёт submission.csv (fake: поиск без bge-m3)
python eval/compare_demo.py                                            # наш ответ рядом с образцом
python eval/demo_eval.py                                               # попал ли нужный пункт в контекст
```

## Как отвечает ассистент

1. Если вопрос содержит диалог, из него берутся последняя реплика пользователя и история. Попытка сменить роль отсекается до вызова модели.
2. Поиск идёт по последней реплике и по реплике вместе с историей. Каналы: dense bge-m3, BM25 или sparse и точный номер статьи или пункта. Результаты сливаются через RRF и пересортировываются реранкером.
3. Короткие документы компании (договор, регламент, письмо) попадают в контекст целиком. Доп. соглашение добавляется к своему договору. У каждого фрагмента в заголовке указана редакция.
4. Генерация (1 вызов LLM): прямой ответ первым, 40–120 слов, ссылки на документ и пункт, метки [S#]. Модель поправляет ошибочные утверждения пользователя, выбирает редакцию по дате события и честно отвечает, если в базе ответа нет.
5. Проверка кодом: метки существуют, каждый номер пункта или статьи, сумма, срок и процент есть во фрагментах или в вопросе, названия законов есть в контексте. На демо-ответах организаторов проверка не дала ни одного ложного срабатывания.
6. Проверка LLM (режим `auto`, ещё 1 вызов): исправляет ответ по фрагментам с учётом найденных проблем. Неподтверждённые предложения удаляются, метки [S#] убираются из текста.

Режим `PIPELINE_MODE`: `fast` — 1 вызов LLM, `auto` — 2 вызова (по умолчанию), `full` — 3 вызова (добавляется разбор вопроса).

## Ограничения

- Работа с настоящими DeepSeek, прокси платформы, bge-m3 и Docker в этом окружении не проверялась: доступа к ним нет. Логика проверена на заглушке, которая отвечает по тем же протоколам (`/chat/completions`, `/embeddings`, `/rerank`). Сабмит запускался в чистом окружении с `httpx==0.28.1` и `numpy==2.2.6`.
- Качество ответов можно оценить только после первого сабмита или прогона с ключом DeepSeek. Промпты (`legal_core/prompts.py`) — главное место для настройки.
- История диалогов хранится в PostgreSQL (том `postgres-data`) и переживает перезапуск. Без `DATABASE_URL` (тесты, запуск без Docker) шлюз держит её в памяти.
- Redis из первоначальной схемы не добавлен: кэшировать пока нечего — эмбеддинги документов посчитаны заранее, а вопросы почти не повторяются.
