# Юридический ассистент ПСБ — описание проекта

Команда: трек ПСБ «Юридический ассистент», Hack&Change 2026.
Репозиторий: https://github.com/Anycrabs/PSB-case (снимок — коммит `2705aa4` от 15.11.2026 23:53 и правки из раздела 9).
Итог на платформе: лучший балл **33.125** — `submission_v3/` (16.11.2026). Сабмиты закончились.

---

## 1. Задача

ИИ-ассистент для юристов компании отвечает на вопросы **только по базе знаний**:
- законы РФ;
- договоры;
- внутренние регламенты.

Требования к ответу:
- ссылается на конкретный документ и пункт;
- поправляет неверные утверждения пользователя;
- выбирает нужную редакцию документа;
- честно отказывает, если ответа в базе нет.

Работает и в диалоге («Пользователь: … Ассистент: …»).

**Как оценивает платформа:**
- **Сабмит:** ZIP с `solution.py` в корне. Платформа запускает его в Docker: 8 CPU, 16 ГБ RAM, лимит 20 минут, 5 сабмитов в день. В среду проверки переносятся только корневые `.py` и `requirements.txt`.
- **Модели** платформа даёт через один OpenAI-совместимый прокси (`LLM_BASE_URL`):
  - DeepSeek V4.1 Flash — генерация;
  - bge-m3 — эмбеддинги;
  - реранкер.
- **Судья-LLM** сравнивает наш ответ с ответом baseline организаторов относительно эталона юристов:
  - два раунда со сменой мест A/B;
  - шкала 1 / 0.75 / 0.5 / 0.25 / 0;
  - выдуманный факт — 0 за вопрос.
- **Итог:** `Score = 0.7 · MatchRate + 0.3 · WinRate`. **50 баллов = уровень baseline.**
- **Логов и вывода запуска платформа не показывает**, обратная связь — только итоговый балл.
- **Для финала** нужен веб-прототип.

## 3. Архитектура прототипа (Docker Compose)

| Сервис | Порт | Назначение |
|---|---|---|
| web | 3000 | Интерфейс; `/api` проксируется на gateway |
| gateway | 8000 | Внешний API `/api/v1`, диалоги, история в PostgreSQL |
| orchestrator | — | Конвейер ответа |
| retrieval | — | Гибридный поиск: Qdrant dense+sparse, BM25, точные ссылки, RRF, реранкер |
| embedder | — | BAAI/bge-m3 (dense + sparse) |
| model-init | — | Один раз скачивает bge-m3 в том `hf-cache` от пользователя `app` |
| indexer | — | Строит индекс из `data/knowledge-base.zip`; пропускается, если архив не менялся |
| qdrant, postgres | — | Векторная БД и история (только внутри сети) |
| fake-llm | — | Заглушка LLM, профиль `dev` |
| platform-proxy | 9100 | Локальная копия прокси платформы (LLM + `/embeddings` + `/rerank`), профиль `eval`; умеет GigaChat |

### Как отвечает ассистент
1. **Разбор вопроса.** Из текста вопроса выделяется диалог (последняя реплика и история). Попытка сменить роль отсекается до вызова модели.
2. **Дата события.** Определяется без LLM: «в августе 2024», «15.08.2024», «в 2024 году» (`legal_core/dates.py`).
3. **Поиск.** Работает по реплике и по реплике с историей, по трём каналам:
   - dense bge-m3;
   - BM25 / sparse;
   - точный номер статьи или пункта.

   Каналы сливаются через RRF, затем реранкер.
4. **Контекст:**
   - короткие документы компании идут целиком;
   - доп. соглашение — рядом со своим договором;
   - у каждого фрагмента в заголовке редакция и пометка «ПРИМЕНЯЕТСЯ / НЕ ПРИМЕНЯЕТСЯ к событию»;
   - если в вопросе есть дата, в контекст добавляется редакция, действовавшая тогда.
5. **Генерация.** Прямой ответ первым, затем ссылки на документ и пункт, метки `[S#]`.
6. **Проверка кодом** (`verify.py`):
   - каждый номер пункта, сумма, срок и процент есть во фрагментах или в вопросе;
   - потерянная оговорка «если иное не установлено…» дописывается.
7. **Проверка вторым вызовом LLM** (режим `auto`): исправляет ответ по фрагментам.

## 4. Запуск прототипа

```powershell
copy .env.example .env          # вписать ключ: DeepSeek (вариант 1) или GigaChat (вариант 2)
docker compose up -d --build    # интерфейс http://localhost:3000, API http://localhost:8000/docs
```

- Первый запуск качает bge-m3 (`docker compose logs -f model-init`).
- Без ключа можно посмотреть интерфейс с заглушкой: `docker compose --profile dev up --build`.
- **Бесплатная LLM для проверок — GigaChat Freemium:**
  1. Ключ авторизации вписать в `GIGACHAT_CREDENTIALS`.
  2. Запустить `docker compose --profile eval up -d --build`.
  3. Убедиться: http://localhost:9100/health → `"upstream":"gigachat"`.

  Подробности — в `docs/LOCAL_EVAL.md`.

## 5. Локальная проверка «как на платформе»

```powershell
docker compose --profile eval up -d
python eval/local_platform.py --set demo --zip submissions\submission_v2.zip
python eval/local_platform.py --rejudge eval_runs\<папка прогона>   # только переоценить судьёй
```

Как устроено:
1. Сабмит запускается в контейнере `python:3.12-slim` с теми же лимитами (8 CPU, 16 ГБ, 20 минут) и переменными, что на платформе.
2. Рядом запускается baseline организаторов.
3. Судья оценивает оба ответа против эталона в два раунда.
4. Результат: `eval_runs/<время>/summary.txt` и `report.csv` (худшие вопросы сверху).

**Ограничение.** Локально и ответы, и baseline, и судья — GigaChat. Baseline на GigaChat почти всегда отвечает «нет информации», поэтому локальный балл завышен и не предсказывает платформу. Полезно другое: сколько наших ответов в `report.csv` совпадает с эталоном по сути. По последнему локальному прогону — 16 из 18.

| v4 | логика примера организаторов (`sample_submission`): тот же отбор документов, фрагменты и промпт, плюс повторы при сбоях | 12 |

**Выводы:**
1. **Разница 1–2 балла — шум судьи**, верить стоит изменениям от 3 баллов.
2. **Чем больше запросов к API платформы, тем ниже балл:**

   | Версия | Запросов к API на вопрос | Балл |
   |---|---|---|
   | submission_8 | ~5 | 32 |
   | + реранкер | ~8 | 27 |
   | + больше потоков | ~5, но параллельнее | 21.7 |

   Похоже, прокси ограничивает нагрузку, и часть вызовов не доходит до модели.
3. **Подъём `max_tokens` до 3000 убирать нельзя:** без него балл 21. DeepSeek V4.1 Flash рассуждает по умолчанию, и рассуждения расходуют `max_tokens`.
   Принимает ли прокси значение 3000, по баллу судить нельзя: на мок-прокси, который его отклоняет, submission_8 выдаёт одни заглушки и завершается без ошибки. В v3 это обработано: при отказе берётся значение платформы.
4. **Правило «начинай отказ со слов „В базе знаний нет"»** появилось вместе с падением 32 → 28. Его в v2 нет.
5. **Судья сравнивает ответы не с примером организаторов.** Пример (`sample_submission`, копия в `eval/baseline_solution.py`) читает из каждого документа только первые 1200 символов. Сабмит v4 повторил его логику (запросы к модели совпадали байт в байт на мок-прокси) и получил 12. Значит, baseline судьи — более сильное решение, а наш RAG (33) почти втрое выше примера.
6. **Устойчивость вызовов и короткий формат ответа балл не сдвинули:** 32 → 33.125 лежит в пределах шума судьи. Причина отставания от уровня baseline (50) без логов платформы не установлена. У лидеров таблицы на 16.11 — 51.
7. **Поиск причиной не является:** на `data/eval/bench.csv` нужный фрагмент попадает в контекст в 48 из 48 вопросов даже на одном BM25. При уменьшении контекста (6 фрагментов, 10 000 символов) — уже 47 из 48, поэтому размер контекста не менялся.

### submission_v2 — что изменено относительно submission_8
- **1 эмбеддинг и 1 вызов модели на вопрос**, простым текстом. В submission_8 было 2–3 эмбеддинга и 2 вызова в JSON.
- **Поиск локальный:** BM25 + векторы + точные ссылки. Реранкер выключен.
- **Потоков ровно `MAX_WORKERS` платформы** (по умолчанию 2, как в примере организаторов).
- **Отказы прокси:**
  - 429/5xx — пауза с учётом `Retry-After` и до 3 попыток;
  - неотвеченные вопросы переспрашиваются вторым проходом в конце;
  - заглушек нет: в крайнем случае ответ — текст лучшего пункта.
- **Добавлено:** редакция по дате события, сохранение оговорок.
- **Без изменений:** нарезка, `MAX_TOKENS` ≥ 3000, BM25 и индекс.
- **Зонд-самопроверка удалён:** он делал сотни запросов после записи ответов.
- **Проверено на заглушке с лимитом 2 одновременных запроса:** 18 из 18 ответов модели и при 2, и при 6 потоках. Отказы прокси отработаны повторами.

Сборка архива v2:
```powershell
Compress-Archive submission_v2\*.py, submission_v2\requirements.txt dist\submission_v2.zip -Force
```

### submission_v3 — что изменено относительно submission_v2
Отличаются три файла: `solution.py`, `lc_prompts.py`, `lc_embeddings.py`. Подробности и таблица проверок — в `submission_v3/README.md`.
- **Вызов модели подстраивается под прокси** и запоминает рабочий вариант на весь прогон:
  - 4xx на большой `max_tokens` — переход на значение платформы (в v2 это стоило лишнего вызова на каждый вопрос, а 403 не обрабатывался);
  - пустой или оборванный ответ — тот же вопрос с меньшим объёмом рассуждений (`reasoning.effort` low, затем none);
  - если прокси поле `reasoning` не принимает — удвоение `max_tokens`.
- **Темп:** если по первым ответам прогон не укладывается во время, рассуждения уменьшаются для всех вопросов; если это не ускоряет, режим возвращается.
- **`submission.csv` пишется сразу после индекса** (текст найденных пунктов, без API) и обновляется каждые 5 ответов. Новые вызовы прекращаются на 930-й секунде, выход — не позже 1020-й.
- **Эмбеддинги:** тайм-аут 45 с на пачку базы и 15 с на вопрос, 2 попытки; при сбое — BM25 и точные ссылки вместо хеш-векторов (с ними 45 из 48 против 48 из 48).
- **Промпт под формат эталона:** 1–3 предложения, только то, о чём спросили, документ и пункт; без меток `[S#]` и встречных вопросов. Дописывание оговорок кодом убрано.
- **Без изменений:** нарезка, поиск, редакции по дате события, `MAX_TOKENS` ≥ 3000.

Сборка архива v3:
```powershell
Compress-Archive submission_v3\*.py, submission_v3\requirements.txt dist\submission_v3.zip -Force
```

## 7. Переменные платформы

`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`, `EMB_MODEL`, `RERANKER_MODEL`, `TEMPERATURE`, `MAX_TOKENS`, `MAX_WORKERS`, `DATA_DIR`. Плюс запасные имена `OPENAI_*`, `GEN_MODEL`, `BASE_URL`.

## 8. Известные ограничения и что дальше

**Ограничения:**
1. **Без логов платформы** причины баллов — выводы из сравнения сабмитов, а не наблюдения.
2. **`submission/solution.py` из ядра** сейчас по умолчанию в простом режиме (`SOLUTION_MODE=lean`), он дал 21. Для платформы использовать `submission_v3/`.
3. **Прототип (`legal_core/`) работает на прежнем промпте** с метками `[S#]`: по ним интерфейс показывает источники на полях. Промпт v3 меток не ставит, поэтому в прототип он не перенесён.

**Что дальше:**
1. Сабмиты закончились; для финала — веб-прототип.
2. Чтобы понять отставание от baseline, нужны реальные ответы DeepSeek V4.1 Flash: прогнать `eval/local_platform.py` с ключом этой модели вместо GigaChat и сравнить ответы с эталоном по `report.csv`.
